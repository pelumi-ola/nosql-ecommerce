# Reflection Report

**Challenges.** The hardest part was choosing shard keys. My first instinct, `createdAt`, would have sent every new order to one shard, and `status` has too few values. Hashing `customerId` spread writes evenly and kept order history on a single shard, but it broke two things: global unique indexes (a unique index must include the shard key) and the operations queue, which became scatter-gather. I solved uniqueness with ObjectId-based order numbers and an email lookup collection, and moved the ops queue to analytics secondaries. Keeping inventory and orders consistent across shards without slow distributed transactions was also difficult; I used atomic stock reservation plus a compensating release (saga).

**Effect of new requirements.** Analytics pushed me to stop running reports on the transactional collections. Aggregations over raw orders would compete with checkout traffic, so I added pre-aggregated rollups (`sales_daily`, `product_daily_stats`) fed by change streams, and Cassandra tables modelled per query for high-velocity events. The availability requirement forced explicit CAP choices: orders and inventory stay consistent (majority writes, so a minority partition rejects writes), while the catalog, rollups and carts accept eventual consistency.

**Improvements.** *Scalability:* write load now scales horizontally by adding shards, and analytics scale independently. *Availability:* every shard is a three-node replica set across three zones, so losing a node or zone triggers automatic failover with no loss of acknowledged orders. *Query performance:* dashboards read a few small rollup documents instead of scanning millions of orders, and catalog reads are served from nearby secondaries and Redis. The cost is extra storage, slightly higher write latency, and analytics that lag by seconds, which I judged acceptable.
